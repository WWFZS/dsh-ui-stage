# 给 DeepSeek Harness 装上开机动画、界面主题和桌面宠物：一个插件的三次"做减法"

> 项目：`dsh-plugin-startup-animation` · MIT · 零运行时依赖
> 仓库：https://github.com/WWFZS/dsh-plugin-startup-animation

## 先说结论

DeepSeek Harness（下称 DSH）的插件生态里，"换外观"这件事被拆得很散：开机动画一个、壁纸一个、宠物一个。装三个插件、占三份资源、互相抢 `body` 上的主题令牌。

`dsh-plugin-startup-animation` 把它们合成一个：**启动画面 + 界面主题 + 桌面宠物**，一套素材库共用，运行时不依赖任何 npm 包，装好即用。

但真正值得写的不是"三合一"这个决定，而是做完之后的三轮返工——每一轮都是把**已经能用的功能删掉一部分**，因为用户的实际反馈是"太花哨了"「不够丝滑」「看不清」。

这篇讲三个问题：

1. 一个"装上就有"的视觉插件，怎么做到**宁可什么都不显示，也不阻塞启动**
2. 壁纸上放文字这件事，为什么不能靠滑杆碰运气，而必须**算**
3. 滑杆手感这种东西，为什么性能优化的答案是"**别让 React 参与**"

---

## 一、启动画面：把"绝不添乱"当第一性原理

开机动画这类插件最常见的失败模式不是"不好看"，而是**把应用弄得起不来**。

DSH 的页面在启动时有一段"开机动画覆盖层"和"应用就绪"之间的竞态。如果覆盖层监听错了事件，或者淡出逻辑卡住，用户看到的就是：应用其实已经好了，但一层动画蒙在前面不走。

这个插件的做法是：**监听应用真正就绪的时刻**，而不是猜一个固定时长。

具体来说，每条失败路径都有时间上界，统一退回宿主原生的启动页：

| 出错的地方 | 用户看到什么 |
|---|---|
| 素材文件不在 | 原生启动页，动画不出现 |
| 编码不支持（比如传了个 `.mov`） | 原生启动页 |
| 自动播放被浏览器策略拦截 | 超时后淡出，不无限等 |
| `webserver/index-inject` 事件签名变了 | 打一条警告日志，**不带动画**正常启动 |

关键设计：覆盖层挂在 `document.body` 上、**不在 `#root` 里**。这一条决定了它不会干扰 React 的水合（hydration）——很多"注入式"视觉插件就是死在这里。

还有两个细节值得说：

**出口不止一个。** 点击、`Esc` / `Enter` / `空格`、或者时长自然结束——四条路都能出去。而且点击跳过不受"最短展示时长"限制：用户想跳过，就是立刻跳。

**时长语义改过一次。** 最早的做法是"最短展示 N 秒，期间不允许跳过"——听起来合理，实际体验是"我按了跳过，它不理我"。现在的语义是：N 秒是**素材必须露脸的最短时间**，而点击跳过**随时有效**。两个诉求不再打架。

## 二、界面主题：字看不看得清，必须是算出来的

这是整个项目里最花功夫的部分，也是踩坑最多的。

### 为什么不能靠滑杆

给界面铺壁纸，最直觉的做法是给几根滑杆：压暗多少、模糊多少、面板多不透明。用户自己调，调到看得清为止。

问题是：**大多数用户不会调，而调错了的后果是"字看不见"**。一张白底壁纸 + 浅色字 = 1.0:1 对比度，界面上什么都读不了，用户只会觉得"这插件坏了"。

所以这个插件的立场是：观感可以调，但**可读性是一条不能靠滑杆碰运气的线**。

### 三件套：取样 → 决策 → 落地

引擎 `lib/wallpaper.mjs` 是一组纯函数，零依赖，宿主和浏览器共用同一份：

```
analyzePixels / analyzeColors  →  画面摘要（平均色、亮度、暗部占比、分散度、p95/p05）
decideTheme                    →  字用亮色还是暗色 + 需要多厚的幕
deriveTokens                   →  翻成一组 CSS 变量，交给渲染层落地
```

几个绕不开的技术点：

**对比度用二分求解，而且必须向上取整。** WCAG 对比度公式里有一段 gamma 曲线，解析解要解四次方程，不值得——二分 40 次就到浮点精度。但**向上取整**这一步是必须的：精确解常是 `0.6173…` 这种值，四舍五入会把它掉到目标线下面。幕多压 0.001 看不出来，少压一点字就糊了。

**最坏区域不能用平均色估。** 平均色只说明"整体偏亮还是偏暗"，说明不了"画面里最亮那块有多亮"。用亮度分布的 `p95` / `p05` 取两端，比 `max`/`min` 稳（单点高光、字幕白边不算数）。

**面板不透明度按这张壁纸反推，不按纯黑纯白。** 早期实现按"壁纸可能是纯白"来算最坏情况，结果面板被算得死实——用户看到的就是"参数全拉到底，壁纸还是透不出来"。改成按实际量到的 `p95`/`p05` 反推，暗壁纸的面板才敢做透。

**不用 `backdrop-filter`。** 这个决定是被用户逼出来的：一开始把 `backdrop-filter: blur()` 挂在三列上，用户看到的是"设置页的字清楚，对话窗口整个是模糊的"——因为 `backdrop-filter` 糊的是元素背后的**所有内容，包括列里自己的正文**。现在模糊只落在壁纸层自己身上。

**绝不碰排版。** 壁纸只接管颜色。字号、字体、行高一个都不动——那是用户自己的设置，改它就是"影响用户看字"。这条有机器可验的测试：生成出来的样式表里，出现 `font-size` / `font-family` 就算失败。

### 出厂即最透

一个反直觉的决定：**默认值不该是"全加满"**。

如果出厂就压暗、就模糊，那"我想看原样壁纸"的用户必须先把每根滑杆拖到底。现在的默认是：面板不盖、画面不压、不糊。**遮挡是往上加，不是从满格往下减。**

代价是面板必须真的很透——而面板一透，字就会糊。解法是把"看画面"和"读文字"拆成两层：面板保持清澈，只在字底下垫一层接近实色的**文字保险层**（气泡、选中行、输入框）。视觉上仍是"壁纸铺满整个界面"，而正文永远站在 ≥ 4.5:1 的面上。

## 三、滑杆为什么不丝滑：别让 React 参与拖拽

这段是刚修完的，也是最有普遍性的一条。

用户反馈原话：「滑杆不够丝滑」。

第一反应是算法慢。量了一下：一次主题面板渲染（5 张预设卡 + 8 个色块 + 1 次读数，共 14 次决策计算）**0.68ms**。纯数学部分 0.5ms 都不到。所以不是算法问题。

问题在渲染链路：

```js
onChange: (event) => {
  const next = Number(event.target.value)
  if (!Number.isFinite(next)) return
  setDrag((prev) => ({ ...(prev || {}), [key]: next }))   // ← 每格都 setState
  sendPreview(key, next)
}
```

`setDrag` 是 React state。**每格拖动事件都触发整个主题面板重渲染**——14 次决策计算全跑一遍，5 张预设卡和 8 个色块全部重建。

单次 0.68ms 看起来不多。但 `input[type=range]` 的 `change` 事件是 60–240 次/秒，加起来就是**每秒几十到上百毫秒的主线程占用**，正好卡在 16.7ms（60fps）的帧预算上。表现出来就是：滑块本身跟手（因为浏览器自己动那个圆点），但整个页面发涩，预设卡和色块的 hover 都变迟钝。

修复思路是**把拖动过程完全移出 React**：

- **每一格**：只改 DOM（滑块 `value` + 右侧读数文本）+ 让壁纸层重画，**零 setState**
- **开始拖 / 松手**：才动 state（只为切 `disabled` 与收尾落盘）

读数元素用 `ref` 直取，所以"0% → 40%"是浏览器直接改 `textContent`，不经过 React 渲染树。

```js
onChange: (event) => {
  const next = Number(event.target.value)
  if (!Number.isFinite(next)) return
  // 只在"这根还没被拖过"时 setState —— 拖 100 格也只渲染 1 次
  if (drag === null || typeof drag[key] !== 'number') setDrag({ [key]: next })
  paintSliderDom(key, next)   // 直接改 DOM
  sendPreview(key, next)
}
```

顺带修了另一个隐性浪费：`presetPreview` 在一次渲染里要被调 14 次，而它内部每次都重跑 `analyzeColors(hint)`——**输入完全一样**。加一层缓存后，一次渲染从 0.68ms 降到 0.36ms（省 47%）。这个优化对拖动没直接帮助（拖动已经不走 React 了），但让松手、回包、hover 这些固定开销也一起降下来。

### 这条改动的测试怎么写

这里有个坑值得单独说：**让测试真的能失败**。

第一版测试断言"拖动期间没有新的样式表写入"，结果我把代码改回"每格 setDrag"，测试**照样通过**——因为测试沙箱里的 `setState` 垫片只是静默改值，根本不触发重渲染。这条件等于没测。

修法是把垫片做得更诚实：`setState` 时如果**值真的变了**就记一笔，测试断言"拖 20 格只更新 1 次 state"。现在把实现改回旧写法，测试立刻报：

```
FAIL 拖了 20 格却更新了 20 次 state（真 React 会整页重渲染 20 次）
```

**一个不会失败的测试，价值是零。** 写完之后要故意把代码改坏，确认它会红。

## 四、顺手修的两个"数据自己变回去"的 bug

用户还报了：「遮罩厚度、壁纸模糊、色彩浓度时不时还原为默认值」。

查下来是两个根因叠在一起：

**① 点预设会删掉滑杆的值（必现）。** 预设卡的点击处理发了五个键，其中三个把滑杆写成 `'auto'`，而宿主把 `'auto'` 解释成**删除这个键**——磁盘上用户调好的值真没了，刷新也回不来。

这行代码是早期加的，当时是对的：那时七套预设各带不同的 `scrim / blur / saturate`，不清残留值就会"点了没反应"。但后来预设精简成五套、三项统一成 `0 / 0 / 1` 之后，这个"清"只剩副作用。**改预设表的时候没人回头看这段清空逻辑。**

**② 回包乱序把新值盖回旧值（偶发）。** 每发一个 POST 都无条件 `setState(回包)`。连着动两根滑杆时两个请求同时在飞，而回包顺序不保证——先发的那个带着旧状态后回来，就把刚调好的值盖回去。刷新一下又好，因为磁盘上一直是对的。

修法：预设卡只发 `{wallpaperPreset, wallpaperGlass}`；加一个单调递增序号，**只采纳最新回包**，过期回包连 `setBusy(false)` 都不许做。

这两个 bug 有个共同特征：**磁盘上是对的，错的是界面状态**。所以用户描述成"时不时自己变回去"——它不是稳定复现，而是取决于你点没点预设、拖动有多快。

## 五、桌面宠物：一个"有且只有一只"的约束

第三条产品线是桌面宠物：透明的小动物浮在界面上，会自己轮播动作，能拖着走，甩出去带惯性撞边弹回来。

技术上值得一提的只有一条**约束**：`page`（页面浮层）和 `global`（全局置顶窗）两档**互斥**。

最早做了三档，其中有个 `both`（都显示）。结果用户截图里出现了**两只一样的宠物**：一只在页面里堆雪人，一只在桌面待机。原因很简单——`both` 让同一只宠物同时以两个独立实例存在，各跑一套 15 秒随机节奏、各有一份物理。

现在的语义是：两档都保证**有且只有一只**。`global` 档是另一个 Electron 透明置顶窗（Windows），它本来就悬在 DSH 上方，所以 DSH 里当然看得见。

另一个坑：宠物"甩完消失再加载"。根因是用 `JSON.stringify(wanted)` 做"要不要重启进程"的指纹，而 `wanted` 里含 x/y 坐标——于是每次落地写盘 → 宿主 sync → 指纹变了 → 杀掉 Electron 重新 spawn → 一两秒后宠物"重新加载出来"。修法是换 `structuralKey()`，指纹只含"哪几只 / 多大"，不含位置。

## 六、为什么坚持零运行时依赖

`package.json` 里 `dependencies` 是空的。这不是洁癖，是**降低失败面**：

- 浏览器半边只从宿主模块表 `require('react')`——不存在"随包打进了一个会和内核版本脱节的库"这种隐患
- 没有构建步骤，装好即用，纯 ESM + 静态素材
- 素材路由自己实现了 `Range` / `ETag`，视频拖动进度和切片缓存都正常

代价是所有东西都得自己写：原子写 JSON、Windows 上文件句柄占用的删除重试、MP4 时长解析（不引 ffprobe，直接读 `moov/mvhd` 盒子）、缩略图生成……但换来的是**升级 DSH 时不会因为某个依赖崩掉**。

## 七、兼容性：承认自己站在不稳定的地基上

这个插件用了两个内核扩展点：`webserver/index-inject`（注入覆盖层与样式）和 `webServer.register`（路由）。**这两个都不是公开稳定 API**，DSH 小版本间可能改名或换签名。

所以策略是**探测式降级**，而不是版本号判断：

| 如果未来的 DSH 改了…… | 会发生什么 |
|---|---|
| `webserver/index-inject` 的事件名或签名 | 打一条警告，不带动画正常启动 |
| `webServer` 服务 | 不提供设置页入口，其余完全不受影响 |
| 设置页插槽 API | 设置入口消失，不抛异常 |

启动日志会同时写插件版本和宿主内核版本——万一哪次升级把动画弄没了，第一眼就该看那一行。

## 最后：三次"做减法"

回头看，这个项目真正的迭代方向不是"加功能"，而是**删**：

- 删掉"整套观感"里的滑杆清空逻辑——因为预设已经不靠它区分了
- 删掉预设里的遮挡值——因为"出厂即最透"比"预设自带压暗"更符合直觉
- 删掉 `backdrop-filter`——因为它糊的是用户要读的字
- 删掉三档宠物位置里的 `both`——因为它必然产生两只
- 删掉拖动过程中的 `setState`——因为它让页面发涩

每次删都是先有人抱怨"太花哨""不够丝滑""看不清"，然后发现多出来的那部分**本来就不该存在**。

这可能是做视觉类插件最反直觉的一课：**用户不会因为你少做了什么而抱怨，只会因为你多做的那一点挡住了他们。**

## 安装

```sh
dsh plugin --profile <你的 profile> add dsh-plugin-startup-animation
```

或者在插件市场里搜包名。

- DeepSeek Harness **0.2.0+**
- Node.js ≥ 22.12.0（跟随 Harness 自带运行时即可）
- 桌面宠物的「全局界面」需要 Windows + 本机 Electron

MIT 许可。开箱自带 7 段视频 / 9 张壁纸 / 9 段语音 + 两只宠物（合计 127 段动作），也支持上传自己的 MP4 / WebM / GIF / PNG / JPG / MP3。

仓库：https://github.com/WWFZS/dsh-plugin-startup-animation
